# LocalForms: FormFactory-style recreation of the 50-form dataset

This directory imports FormFactory's implementation pattern and uses it to serve
this repo's own 50 forms as a second, non-Google-Forms platform for the interface
comparison described in `docs/ALTERNATIVE_PLATFORM_PLAN.md`.

## What was imported from upstream

`upstream/` is an unmodified clone of
[formfactory-ai/formfactory](https://github.com/formfactory-ai/formfactory)
(commit `b7ef0d669d77d2afd41ff4d51ab31becbdeff30b`), kept for reference and citation.
It is a Flask app: `app.py` with one route per form, Jinja templates extending a
shared `base.html`, Bootstrap 4.5.2 form markup (`mb-3`/`form-label`/`form-control`/
`form-select`/`form-check` classes), and POST submissions logged to
`submission/<form>.json`.

## What `site/` is

`site/` is generated by `scripts/generate_localforms.py` from
`src/forms/*/spec.json` (this repo's 50 form specs) and directly reproduces that
pattern:

- One Flask route per form (`/forms/lf_<form_id>`), built from a manifest loop
  instead of 50 hand-duplicated route functions, but functionally identical to
  upstream's one-route-per-form design.
- The same Bootstrap 4 form markup and template-inheritance structure as
  upstream's `templates/*.html` + `base.html`.
- The same POST-submission JSON logging (`save_submission_to_json`).
- Bootstrap 4.5.2 CSS vendored locally (`static/css/bootstrap.min.css`) instead of
  loaded from upstream's CDN link, so the site renders identically on HPC compute
  nodes without outbound network access.

## Two additive adaptations (why, and why they're safe)

This repo's existing scoring pipeline (`src/engine/mcp_browser_engine.py`,
`src/engine/form_engine.py`) locates and reads form fields with two conventions
that Google Forms happens to satisfy natively. Upstream FormFactory forms don't
use these conventions (it has its own separate Flask-based evaluator instead), so
reusing *this* repo's verifier — required to keep scoring identical across the
Google Forms and LocalForms conditions — means the generated templates add:

1. **`role="listitem"` per question, inside a `role="list"` wrapper.** The
   verifier finds a question by scanning `div[role='listitem']` elements for
   matching label text. This is valid ARIA and is what Google Forms itself does;
   it does not make any field easier to answer, only easier to locate as "the
   Nth question."
2. **Explicit `role="radio"` / `role="checkbox"` and `aria-label="<option text>"`
   on each native `<input type="radio">` / `<input type="checkbox">`.** Native
   HTML controls carry these roles *implicitly* in the real accessibility tree
   (which is what the model's own Playwright-MCP tool calls use, via
   `aria-ref` — so the model sees these correctly either way). The verifier,
   however, reads selection state with a literal `[role='radio']` CSS attribute
   selector, which does not match implicit roles. Making the role explicit is
   the smallest fix that keeps the same verifier code working across both
   platforms; it is standard, valid, redundant-but-harmless ARIA usage.

Both are documented in `docs/ALTERNATIVE_PLATFORM_PLAN.md` and were required
specifically because this comparison holds the *scoring policy* constant, not
because upstream FormFactory itself needs them.

## One functional finding from validation (date/time widgets)

Native `<input type="date">` / `<input type="time">` do not reliably accept
character-by-character simulated typing in headless Chromium (`locator.type()`):
a live probe showed the time value ending up empty and the date value garbled
after typing, while `locator.fill()` on the same elements worked correctly. Since
both the model-driven MCP tools and this repo's scripted reference engine type
character-by-character rather than filling directly, native date/time inputs
would have silently zeroed a real fifth of all fields (73 of 409, DATE+TIME)
across the whole comparison.

The generator therefore renders DATE and TIME questions as plain
`<input type="text">` with a placeholder and a `Format: YYYY-MM-DD` /
`Format: HH:MM (24-hour)` hint — matching upstream FormFactory's own style, which
does not use native date/time pickers either (its templates use plain text
inputs throughout). `src/engine/mcp_browser_engine.py`'s `readTimeValue` and
`src/engine/form_engine.py`'s `_handle_time`/`_read_time_value` gained a
single-text-input fallback branch mirroring the one `readDateValue` already had,
so both engines read/fill a lone text input the same way regardless of platform.
This was caught and fixed by a zero-GPU pre-flight check (scripted Playwright
fill+verify against the generated pages, no model involved) before any GPU time
was spent — see the validation log referenced from
`docs/ALTERNATIVE_PLATFORM_PLAN.md`.

## Regenerating

```bash
.venv/bin/python3 scripts/generate_localforms.py
```

Regenerates `site/templates/`, `site/app.py`, `src/forms_localforms/lf_*/spec.json`,
and `data/answers_localforms/lf_*/runs.json` deterministically from
`src/forms/*/spec.json` and `data/answers/*/runs.json`. Safe to rerun any time the
50 source specs change.

## Running locally

```bash
.venv/bin/python3 site/app.py --host 127.0.0.1 --port 5055
```

Then point a baseline eval at it with the additive `--forms-root` / `--form-url`
overrides added to `src/baselines/run_qwen_direct_mcp_eval.py`:

```bash
.venv/bin/python3 src/baselines/run_opencua_direct_mcp_eval.py \
  --config configs/baselines/track_baseline_models.json \
  --model-id computer_use_opencua_32b_direct_mcp \
  --form-id lf_conf_interest \
  --forms-root src/forms_localforms \
  --form-url http://127.0.0.1:5055/forms/lf_conf_interest \
  --answers-root data/answers_localforms \
  --run-index 2 \
  --fill-only-done
```

On Slurm, `scripts/slurm_opencua_direct_mcp_localforms.sbatch` starts this Flask
app as a second background service alongside the vLLM server (distinct,
job-id-derived port so concurrent jobs never collide), then runs
`scripts/run_opencua_direct_mcp_localforms_matrix.sh` for the requested
`FORM_IDS`/`RUN_INDEXES`.
